# mindHR v0.2.0 — Release Plan: "Admin Dashboard & Attendance Operations"

> Status: **Planned** · Owner: mindHR team · Last updated: 2026-11-07
> Based on a gap analysis against a competitor organisation admin panel (PiHR) and the current mindHR code.

---

## 1. Goal

Today an organisation admin who logs in sees only a welcome card (`DashboardPage.tsx`). To learn anything they
must open each module separately. The goal of v0.2.0 is:

> **When an HR admin or manager logs in, they see in one screen what needs their attention today,
> and they can act on it in one or two clicks.**

Secondary goals:
- Make attendance and payroll **correct on public holidays** (today payroll assumes "Friday off, no holidays").
- Stop losing real check-ins that happen outside the geofence (field work, WFH, GPS drift).
- Close the open **security gap** on `/api/users` and `/api/roles` before the first public deploy.
- Deploy the backend on **Render** so the mobile app can use a public API.

### Non-goals (later releases)
Break time, field visits, overtime calculation, Excel attendance import, notice board, KPI, Tax, push
notifications (FCM). See [section 9](#9-deferred-to-v030).

## 3. Blockers

### R0 — Permission checks on users and roles

**Problem.** `UserController` and `RoleController` have no `@PreAuthorize`. Any signed-in org user, even an
`EMPLOYEE`, can list all users/roles of their organisation and probably call `PUT /api/users/{id}` with
`roleIds` to make themselves `ORG_OWNER` (privilege escalation).

**Change.**
- Add permission modules `USER` and `ROLE` (`VIEW`, `CREATE`, `UPDATE`, `DELETE`) in the permission seed.
- Give them to `ORG_OWNER` and `HR_ADMIN` in `OrgRoleProvisioner`; `OrgRoleBackfillRunner` adds them to existing orgs.
- `@PreAuthorize("hasAuthority('USER_VIEW')")` etc. on every endpoint.
- **Extra rule:** a user must never assign a role whose `dataScope` is wider than their own (e.g. an `HR_ADMIN`
  cannot grant `ORG_OWNER`). Check this in the service, not only in the controller.
- `GET /api/account/me` (or the existing account endpoint) stays open so users can read their own profile.

**Done when.** The two `KNOWN ISSUE` checks in `scripts/api_e2e_test.py` pass and are renamed to normal checks;
new check: `qa.emp1` gets 403 on `GET /api/users` and on `PUT /api/users/{id}`.

### R1 — Deploy on Render

Done in this release:
`master` merged into `main`, root `render.yaml` blueprint (`rootDir: backend`), `server.port=${PORT:8080}`, JVM heap cap, fixed `.dockerignore`.

**Remaining steps.**
1. ~~Merge `master` into `main`.~~ Done.
2. Render → New → Blueprint → set `DB_URL`, `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` (`JWT_SECRET` is generated by Render).
3. Build the mobile app with `-PapiBaseUrl=https://<service>.onrender.com/`.
4. Change the seeded SUPER_ADMIN password right after first login.

**Known limits.** Free plan sleeps after 15 min idle (first call ~30–60 s). If the React app is later hosted on a
different domain, the backend needs a CORS config (today it relies on the Vite / nginx proxy).

## 4. P0 features

### F1 — Dashboard summary

**User story.** As an HR admin / branch manager, I open the dashboard and see counters for everything that needs
attention today, limited to the employees I am allowed to see.

**API.** `GET /api/dashboard/summary?organizationId=` (organizationId only for platform users, like other org endpoints)

```json
{
  "date": "2026-11-07",
  "headcount": 88,
  "attendanceToday": { "present": 54, "late": 9, "absent": 11, "onLeave": 4, "notCheckedIn": 10 },
  "onLeaveToday": 4,
  "onLeaveTomorrow": 1,
  "pendingLeaveRequests": 3,
  "pendingWorkRequests": { "SALARY_ADVANCE": 1, "WORK_FROM_HOME": 2, "ATTENDANCE_CORRECTION": 0, "...": 0 },
  "pendingRemoteAttendance": 0,
  "upcomingBirthdays": 2,
  "monthlyClaimAmount": 1200.00,
  "monthlyDisbursedAmount": 800.00
}
```

`pendingRemoteAttendance` arrives with F5 and `upcomingBirthdays` with F8. Until then they return `0`.

**Backend design.**
- New `DashboardService` + `DashboardController`. Permission: user must hold at least one `*_VIEW` HR authority;
  each block is only filled if the user has that module's permission (e.g. no `LEAVE_VIEW` → `null` leave block).
- **One aggregate query per block** (`COUNT(*) ... GROUP BY status`), not "load the lists and count in Java".
- Row filter: `DataScopeService.visibleEmployeeIds(orgId)` → `WHERE employee_id IN (:ids)`; for `ORGANIZATION`
  scope skip the `IN` and filter by `organization_id` only (faster for big orgs).
- Claim / disbursed amount: sum of `WorkRequest.amount` for `EXPENSE` (+ `SALARY_ADVANCE`, `LOAN`) this month,
  status `APPROVED` (claimed) and paid (disbursed — needs a `PAID` state or payroll link; if not available, ship only "approved").
- Indexes to check/add: `attendance(organization_id, work_date)`, `leave_requests(organization_id, status)`,
  `leave_requests(employee_id, from_date, to_date)`, `work_requests(organization_id, status)`.

**Frontend.**
- `src/api/dashboard.ts` + types in `src/api/types.ts`.
- `DashboardPage.tsx`: keep the welcome card; add a responsive grid of counter tiles (Bootstrap cards, `react-feather` icons).
- Every tile links to the filtered list (e.g. "Pending leave" → `/leave?status=PENDING`).
- TanStack Query with `staleTime: 60_000` — counters do not need to be real-time.

**Done when.** The dashboard shows correct numbers for `qa.owner` (whole org), `qa.lead` (team only) and
`qa.emp1` (sees self-service view, not org counters). E2E script has checks for all three.

> **Learning note — read models.** The dashboard is a *read model*: an endpoint shaped for one screen, built from
> aggregate queries. This is the "Q" side of CQRS without the complexity of separate databases. If it becomes slow,
> the next step is a short cache (Caffeine, 30–60 s, key = orgId + scope + employeeId), not a new table.

### F2 — Today's attendance quick view

**User story.** As a manager, I see every visible employee with today's status, in time and out time, and I can
filter by status with one click.

**API.** `GET /api/attendance/today?organizationId=&status=&branchId=&departmentId=&q=`
Returns one row **per employee** (not per attendance record):

| field | note |
|---|---|
| employeeId, employeeCode, fullName, position, branchName | |
| status | `PRESENT`, `LATE`, `ABSENT`, `ON_LEAVE`, `HALF_DAY`, `HOLIDAY`, `WEEKEND`, `NOT_CHECKED_IN` |
| checkInAt, checkOutAt, lateMinutes | null if no record |

Status is **derived**: approved leave covering today → `ON_LEAVE`; holiday (F3) → `HOLIDAY`; weekly off → `WEEKEND`;
attendance record → its status; otherwise `NOT_CHECKED_IN` (becomes `ABSENT` after the shift end / end of day).
This is a view model; do **not** add `NOT_CHECKED_IN` to the `AttendanceStatus` enum.

**Frontend.** "Quick View" card on the dashboard: status chips with counts (All / Present / Late / Absent / Leave / …),
search box, table. Row action "Add record" opens the existing `AttendanceForm` pre-filled (needs `ATTENDANCE_MANAGE`).

### F3 — Holiday calendar

**Why P0.** Without holidays, payroll marks everyone absent on Eid and deducts a day; the attendance view shows
"Absent" on holidays. Three modules depend on it, so it should be built once, early.

**Entity** `Holiday extends Tenant` (table `holidays`):

| column | type | note |
|---|---|---|
| name | VARCHAR(150) | "Victory Day" |
| date | DATE | one row per day; a 3-day Eid = 3 rows or `from_date`/`to_date` (choose **from/to**) |
| from_date, to_date | DATE | inclusive |
| branch_id | FK nullable | null = whole organisation |
| type | VARCHAR(30) enum `HolidayType` | `PUBLIC`, `COMPANY`, `OPTIONAL` |
| paid | BOOLEAN | default true |

Unique-ish rule: no overlapping holidays with the same name and branch (service check).

**API.** Standard CRUD `/api/holidays` (permission module `HOLIDAY`: VIEW for everyone in the org, MANAGE for HR),
plus `GET /api/holidays?from=&to=` for calendars.

**Integration.**
- `HolidayService.isHoliday(orgId, branchId, date)` and `holidaysBetween(orgId, branchId, from, to)`
  (load the range once — don't query per day inside loops).
- `PayrollService`: working days = days in month − weekly off − paid holidays; a holiday with no attendance is **not** absent.
- `LeaveRequest` days: exclude weekly off and holidays when counting leave days.
- Attendance check-in on a holiday: allowed, flagged (future OT).
- Weekly off day: move "Friday" from code into `OrganizationSetting` (`weekly_off_days`, default `FRIDAY`) at the same time.

**Frontend.** "Holidays" tab under Leave (list + form). Optional: "Copy last year's holidays" button.

**Migration note.** New table only, no enum changes → safe with `ddl-auto=update`. If `AttendanceStatus` later gets
`HOLIDAY`, add `attendance.status` to `EnumCheckConstraintRunner.COLUMNS`.

> **Learning note — single source of truth.** Payroll, leave and attendance each had their own idea of "a working
> day". Pulling it into one `WorkCalendarService` (weekly off + holidays + later roster) removes a whole class of
> bugs where two modules disagree.

## 5. P1 features

### F4 — Leave calendar

- Month grid (Sun–Sat), each day shows approved leaves (avatar/initials) and holidays (F3) with a coloured legend:
  Approved / Pending / Today / Holiday. More than 2 entries → "+N others" popover.
- Filters: leave type, branch, department.
- API: reuse `GET /api/leave-requests?from=&to=&status=` (add range params if missing) + `GET /api/holidays?from=&to=`.
- Respect data scope (a team lead sees only the team).
- Library: a small custom grid is enough (no heavy calendar dependency); `date-fns` for date math.

### F5 — Soft geofence + remote attendance approval

**Today.** `AttendanceActionService` **rejects** GPS/selfie check-ins outside the branch radius.

**New behaviour (per-organisation setting `attendance.outsideGeofence` = `REJECT` | `REQUIRE_APPROVAL`, default `REQUIRE_APPROVAL`).**
- Check-in outside the radius is saved with `approvalStatus = PENDING`, `distanceM`, and an optional `remark`
  ("worked from home", "client visit").
- Inside the radius → `approvalStatus = AUTO_APPROVED`.
- Pending records **do not count** as present for payroll until approved; rejected → treated as absent.

**Entity changes (`Attendance`).**

| new column | type |
|---|---|
| check_in_distance_m, check_out_distance_m | INTEGER |
| approval_status | VARCHAR(30) enum `AttendanceApproval` (`AUTO_APPROVED`, `PENDING`, `APPROVED`, `REJECTED`) default `AUTO_APPROVED` |
| remark | TEXT |
| approved_by_id, approved_at | FK employee, TIMESTAMP |

Existing rows get `AUTO_APPROVED` (set a column default, or a startup backfill — `ddl-auto=update` adds the column as NULL).

**API.**
- `GET /api/attendance/approvals?status=PENDING&from=&to=` — list with employee, type (In/Out), time, distance, remark.
- `POST /api/attendance/{id}/approve` and `/reject` (body: `note`) — permission `ATTENDANCE_APPROVE`
  (new action), scope-checked with `DataScopeService.assertCanAccess`.

**Address.** PiHR shows a reverse-geocoded address. Do it **client-side on the mobile app** (Android `Geocoder`,
no API key) and send `checkInAddress` with the check-in; store it as TEXT. No server-side geocoding API needed.

**Mobile.** The check-in sheet already shows the distance; when outside, show "Outside office area — your manager
will need to approve" + an optional remark field instead of an error.

> **Learning note — soft vs hard constraints.** A hard rule (reject) is simple but loses real data and pushes people
> to workarounds. A soft rule (accept + flag + human review) keeps the truth and moves the decision to someone with
> context. Fraud detection, expense systems and content moderation all use this pattern. The cost: you need a
> review queue and a clear rule for what "pending" means downstream (here: payroll ignores it until approved).

### F6 — 30-day attendance summary chart

- API: `GET /api/attendance/summary?from=&to=` → `[{ date, present, late, absent, onLeave, holiday }]`
  (one `GROUP BY work_date, status` query + holidays + leave).
- Frontend: stacked bar chart on the dashboard (Recharts or Chart.js — pick one and use it everywhere).
  Colours from `frontend/src/styles/colors.css`.

## 6. P2 features

### F7 — Missed attendance report
Employees who were **expected** to work (has a shift assignment / not weekly off / not holiday / not on leave) but
have no check-in, or a check-in without check-out. List with date range filter; row action "Create correction"
(opens an `ATTENDANCE_CORRECTION` work request or a manual record for HR).

### F8 — Birthdays
- `Employee.dateOfBirth` (DATE, nullable) — add to DTOs, `EmployeeForm`, Postman.
- Dashboard tile + list "Upcoming birthdays (next 7 days)". Query must handle year wrap (Dec 28 → Jan 3):
  compare `(month, day)` pairs, not dates.
- Privacy: show day and month only, never the year.

### F9 — Leave balance table
Add branch/department filters and sortable "remaining" / "taken" columns to `LeaveBalancesTab`.

## 7. Cross-cutting

### Permissions (new)
| Module | Actions | Default roles |
|---|---|---|
| USER, ROLE | VIEW, CREATE, UPDATE, DELETE | ORG_OWNER, HR_ADMIN (HR_ADMIN cannot grant wider scope) |
| HOLIDAY | VIEW, MANAGE | VIEW: all; MANAGE: ORG_OWNER, HR_ADMIN |
| ATTENDANCE | + APPROVE | ORG_OWNER, HR_ADMIN, BRANCH_MANAGER, TEAM_LEAD |
| DASHBOARD | — (uses existing module VIEW permissions) | |

New permissions must be added to existing orgs by `OrgRoleBackfillRunner`. Remember: JWT claims change only at next login.

### Plan limits
- Dashboard: all plans.
- Remote approval & holiday calendar: part of `ATTENDANCE` / `LEAVE` features (no new `PlanFeature`).
- Charts: consider gating advanced reports behind `REPORTS` in a later release.

### Database changes summary
| Change | Risk with `ddl-auto=update` |
|---|---|
| New table `holidays` | none |
| `attendance`: 6 new columns | low — set defaults / backfill `approval_status` |
| `employees.date_of_birth` | none |
| New enum values in existing enum columns | **must** add to `EnumCheckConstraintRunner.COLUMNS` |
| New indexes | add with `@Table(indexes = ...)`; check on Neon with `EXPLAIN` |

> Consider introducing **Flyway** in this or the next release. `ddl-auto=update` never drops/renames columns, can't
> backfill data, and is risky on a shared production DB. Start with a baseline migration of the current schema.

## 11. Risks

| Risk | Mitigation |
|---|---|
| Dashboard queries slow on Neon (remote DB, cold starts) | aggregate queries + indexes + 60 s cache; measure with `EXPLAIN ANALYZE` |
| Payroll results change for past months after holidays are added | holidays affect only **draft** payroll runs; finalized runs are never recalculated |
| Pending remote check-ins forgotten → wrong payroll | dashboard tile + block payroll finalize while pending items exist for that month (warning with override) |
| `ddl-auto=update` + new enum values | `EnumCheckConstraintRunner`; plan Flyway |
| Render free plan sleeps | acceptable for testing; paid instance before real customers |
